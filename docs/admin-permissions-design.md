# 普通管理员动态权限设计

状态：已落地到 user-center 的 `/dashboard`。权限结构已合并到 `001_init.sql`。

实现适配：当前项目已移除 `auto_access`，改用注册与邀请流程。因此 `apps.manage` 管理应用资料与启停，注册策略、审批及集成诊断维持超级管理员专属；不重新引入旧的自动授权字段。用户创建复用现有邮箱邀请流程。

## 1. 方案范围

保留 `super_admin`、`admin` 两种固定身份，新增“普通管理员 → 全局权限”和“普通管理员 → 应用 → 应用内权限”的直接授权关系。超级管理员在现有管理员页面按模块、应用勾选、保存或清空权限。权限项由代码定义，授权结果存数据库。

本期不增加自定义角色、角色继承、权限表达式、显式拒绝或外部策略服务。相同岗位可以在 UI 中使用快捷选择，但快捷选择只填充勾选项，不形成新的权限实体。

动态分配指随时调整某个管理员拥有的权限，不允许在后台随意创建权限代码。新增业务能力必须随代码增加权限定义和校验。

本期纳入应用范围，应用内权限必须绑定具体 app_id。可分别授权“管理 A、只读 B、不可见 C”；权限和应用不能拆成两个集合后做笛卡尔积，也不允许将一个应用的操作权限用于另一个应用。

全局权限用于共享用户账户、身份提供方摘要、全局日志及通知运维；应用内权限用于应用配置、所属客户端及该应用的成员访问资格。应用权限绝不隐含全局用户管理能力。首期仅支持显式选择已有非系统应用，无动态“所有当前及未来应用”范围；“全选当前应用”只保存当时勾选的具体应用 ID。新应用默认不在任何普通管理员范围内。

## 2. 当前实现及接入点

- `web/dashboard/guard.rs` 与导航共用 `admin::can_access_dashboard`，放行 `super_admin` 和 `admin`，两者均要求完成 MFA；非管理员拒绝访问。首页、个人中心和后台共用 `can_access_dashboard` 导航字段，细分菜单与操作授权尚未实现。
- `web/dashboard/mod.rs` 集中注册后台路由，适合显式绑定操作权限。
- `web/security_gate.rs` 已对后台写操作要求近期认证；继续复用 MFA、CSRF 和五分钟内认证。
- `service/admin.rs` 已有角色变更、策略事务锁、最后一个超级管理员保护及目标会话撤销。
- `web/dashboard/audit.rs` 已有后台 POST 的 pending/结果审计，但授权变更需要补充结构化差异。
- `DashboardLayout` 和前端菜单目前没有细分权限；应用、用户和提供方详情还会聚合其他模块数据，必须同时调整响应内容。
- `services/admin` 是独立 OAuth 登录入口；本次授权策略实施在实际承载管理功能的 user-center。OAuth scope、系统应用访问资格和管理权限继续独立。

## 3. 权限项：按业务能力分组

建议首期采用以下 19 项；不按按钮数量拆分，也不使用笼统的 `dashboard.write`。前七项用户权限和后五项提供方/日志/通知权限为全局，其余七项绑定具体应用。

| 模块 | 权限代码 | 能力与边界 |
| --- | --- | --- |
| 用户 | `users.read` | 查询非管理员用户、基础资料；联系方式脱敏 |
| 用户 | `users.sensitive.read` | 在基础查询之上查看完整邮箱、手机号；不包含凭据 |
| 用户 | `users.create` | 创建普通用户；不能携带管理员身份或权限 |
| 用户 | `users.update` | 修改昵称、头像等资料；不能改邮箱、手机号、密码、状态 |
| 用户 | `users.contact.update` | 修改普通用户邮箱、手机号；保留现有验证状态清除和凭据失效逻辑 |
| 用户 | `users.status.update` | 启停普通用户；沿用会话/凭据失效逻辑 |
| 用户 | `users.password.reset` | 重置普通用户密码；沿用会话撤销，不影响 MFA |
| 应用 | `apps.read` | 查询指定应用基础资料 |
| 应用 | `apps.manage` | 编辑、启停指定应用；属于高影响权限；不包含新建应用 |
| 客户端 | `clients.read` | 查看指定应用的客户端配置；无 secret/hash |
| 客户端 | `clients.manage` | 创建、编辑、启停指定应用的客户端；允许修改回调、类型、scope、TTL 等，属于高影响权限 |
| 客户端 | `clients.secret.rotate` | 单独更换指定应用的既有客户端 secret、查看本次生成值 |
| 应用成员 | `apps.members.read` | 查看指定应用的非管理员成员摘要及访问状态；无联系方式、身份列表、其他应用关系 |
| 应用成员 | `apps.members.manage` | 向指定应用添加非管理员成员或撤销成员访问资格；不修改共享账户 |
| 身份提供方 | `providers.read` | 仅查看提供方和密钥的非敏感摘要，不含密钥或解密后的配置 |
| 日志 | `events.read` | 查询全局登录记录，包含 IP 等敏感元数据 |
| 审计 | `audit.read` | 查询全局操作审计，无修改/删除能力 |
| 通知 | `notifications.read` | 查看脱敏投递记录与汇总，不包含通知载荷和验证码 |
| 通知 | `notifications.retry` | 重试符合现有条件的通知，不允许改收件人、载荷或有效期 |

权限依赖显式定义：所有 `users.*`（除 `users.read`）依赖 `users.read`，其中 `users.contact.update` 还依赖 `users.sensitive.read`；应用内 `apps.manage`、`clients.read`、`apps.members.read` 依赖同一应用的 `apps.read`，`clients.manage`、`clients.secret.rotate` 依赖同一应用的 `clients.read`，`apps.members.manage` 依赖同一应用的 `apps.members.read`；`notifications.retry` 依赖 `notifications.read`。应用内的依赖不能由另一个应用的授权满足。

保存时校验完整依赖集合，缺少依赖则拒绝并提示；前端联动勾选只是便利。取消基础权限时，前端一并取消其依赖者并在提交前显示最终差异，后端依然独立校验。不存在自动授予其他写权限的规则。

以下操作仅限超级管理员，不进入可分配目录：管理员列表及身份变更、权限分配、新建应用、系统应用及其客户端操作、身份提供方创建/修改/启停、签名密钥生成/激活/撤销。新应用由超管创建并明确分配，创建结果不自动赋予普通管理员权限。提供方与签名密钥控制全站认证信任，首期不开放给普通管理员。

## 4. 授权与防越权规则

### 4.1 分配权限不等于持有权限

只有当前有效的超级管理员可以修改普通管理员权限。普通管理员即使拥有目录中全部权限，也不能授权、转授、改管理员身份或修改超级管理员权限。不存在可勾选的 `permissions.manage`，也不存在 `*` 通配授权。

保存 API 从当前会话识别操作者，不接受表单中的 actor；必须在事务内重新验证操作者身份、会话、MFA 和近期认证。目标必须是有效 `admin`，不能是超级管理员或普通用户。未知、保留、作用域类型错误及依赖不完整的权限代码整笔拒绝，不静默忽略。每个应用 ID 必须存在、未删除且为非系统应用；禁止将 `users.password.reset` 等全局权限放进应用授权，或把 `clients.manage` 放进全局权限。

超级管理员不保存权限明细，通过明确的超级管理员身份分支获得管理能力，但仍受会话、MFA、近期认证、CSRF 和业务约束限制。

### 4.2 防止通过业务功能间接提权

普通管理员不能通过后台业务接口修改任何管理员账户，包括自己；密码、联系方式、资料、状态和应用访问资格均执行同一保护。自己的资料通过个人中心修改。身份被提升为管理员时，正在进行的普通用户写入也必须重新检查目标身份。

普通管理员的用户列表、搜索、详情和应用授权目标选择器排除全部管理员。直接提交管理员 UUID 返回 404。保护在服务事务内实施，不能只过滤列表。

系统应用、其 OAuth 客户端及系统应用访问资格同样不能被普通管理员修改或查询详情；客户端归属通过数据库解析，不能相信表单中的 app_id。普通管理员不能把普通应用变成系统应用，创建/编辑接口拒绝 system 等保留字段。

`clients.manage` 必须标为高影响：修改 redirect_uri、本身就可能控制应用的登录结果，不能被描述为低风险配置权限。`apps.manage` 可启停应用，会影响应用访问。授权界面需要说明这些实际能力。

`clients.secret.rotate` 分离的是既有客户端密钥轮换能力，并不意味着 `clients.manage` 无法影响应用安全。创建 confidential 客户端由 `clients.manage` 授权并允许返回新建 secret；编辑已有客户端时，非空 secret、类型切换导致密钥创建/清除等情况必须额外要求 `clients.secret.rotate`，避免绕过 reset-secret 接口。

现有用户资料编辑表单同时含邮箱、手机号；必须拆分资料和联系方式动作或对变化字段分别鉴权。不能让 `users.update` 间接获得 `users.contact.update`。不得接受不属于当前动作的敏感字段并忽略校验。

### 4.3 功能、对象、字段三层同时检查

允许执行 = 有效管理员会话 + 目标范围内的对应操作权限 + 目标允许管理 + 字段符合权限 + 原有业务约束。

后端统一提供 `can_global(permission)` 和 `can_app(app_id, permission)`，权限类型固定，不做缺省范围或跨范围回退。例如 A 有 `clients.manage`、B 仅有 `apps.read` 时，在 B 创建客户端必须拒绝；不能因“某处有 clients.manage”而放行。

客户端请求先从数据库解析真实 app_id，再校验该应用内权限；创建客户端时检查目标应用，编辑时 app_id 不可变，拒绝借更新把客户端移动到其他应用。路径与表单若同时提供应用 ID，必须一致。成员访问变更同时检查应用范围及目标用户不是管理员。

路由统一做功能校验，服务层做对象和字段校验。现有只收 db/id/input 的管理写服务应接收可信操作者上下文；任何后台调用入口都必须经过同一服务授权。新增后台路由未声明权限时默认拒绝，GET、POST 和 HEAD 均不能绕过。

缺少全局操作权限返回 403；对象不存在、受保护或不在应用范围内统一返回 404，不暴露范围外应用是否存在；已可见应用内缺少写权限返回 403。授权依赖不可用返回 503，不降级放行。权限错误需调整现有 `management_response` 中统一映射成 400 的行为。

### 4.4 应用成员与共享用户账户

仅有应用授权的管理员从应用详情进入“成员”页，不需要 `users.read`，也不能借此进入全局用户详情。成员列表按该 app_id 的现有访问关系查询，仅输出 user_id、username、nickname、该应用的访问状态；排除管理员账户，不附带账户全局状态、联系方式或其他应用关系。

添加成员允许持有该应用 `apps.members.manage` 的管理员按完整用户名精确指定一个已有有效非管理员用户。可提供带 CSRF 的精确候选解析 POST，返回最少摘要；不提供全局模糊搜索、分页目录、邮箱/手机号查人。不存在、不可添加或为管理员统一返回不可用结果。该能力会允许确认所知用户名是否可添加，属于成员管理的明确边界，需要速率限制且不记录查询正文。

撤销成员仅撤销目标应用的访问资格并沿用该应用相关凭据失效逻辑，不能撤销全局 SSO 或影响其他应用。撤销访问不是永久禁止后续通过注册或邀请流程重新获得资格，界面需说明。

重置共享用户密码、修改其联系方式或停用账户会影响其他应用，不能按“该用户也是 A 的成员”授权。这些操作始终要求显式授予的全局 `users.*` 权限；全局用户权限不自动获得任何应用的成员管理权限。

## 5. 数据泄漏控制

- 应用列表仅包含持有 `apps.read` 的具体应用；`apps.read` 不附带客户端配置，详情只有在同一应用另有 `clients.read` 时查询并序列化客户端区块，成员区块同样要求该应用的 `apps.members.read`。
- 全局用户详情中的完整联系方式要求 `users.sensitive.read`；登录记录要求全局 `events.read`，缺失时不查询、不输出。应用访问关系也按每个应用的 `apps.members.read` 过滤，不能因为有全局用户读取权限就返回所有应用名或关系。可授予应用的选择器只包含当前管理员持有 `apps.members.manage` 的应用；`users.read` 不满足应用授权检查。
- 用户编辑页无 `users.sensitive.read` 时不返回完整联系方式；资料修改接口采用独立输入，避免脱敏占位符回写。联系方式变更页要求同时拥有 `users.contact.update` 和 `users.sensitive.read`。
- 提供方普通只读响应仅包含明确允许的摘要字段，不复用含 client_secret、settings 或私钥的持久化模型。
- 密码、密钥哈希、加密载荷、TOTP secret、恢复码绝不因任何普通管理员权限而返回。新建/轮换客户端 secret 仅在本次成功响应中显示，沿用敏感响应处理，禁止进入日志、审计正文或客户端持久化缓存。
- 通知重试权限只改变原消息调度状态，不能借重试接口读取验证码、恢复链接或完整收件地址。
- 全局审计、登录记录、提供方摘要及通知运维是明确授予的全局能力，界面单独标注；应用授权不授予这些能力。现有日志/通知缺少可靠应用归属时不根据用户所属应用推断归属，不向应用管理员开放相关区块。
- 列表、计数、搜索结果和下拉选择器在数据库查询时应用相同过滤，不能取出完整数据后仅在 UI 隐藏。
- 管理 JSON 与敏感响应使用 `Cache-Control: no-store`；退出、账号切换和收到 403 时清理前端管理缓存。已交付浏览器的数据不能靠撤权追回，撤权保证后续请求受新策略控制。

## 6. 最小存储模型

保留 `admin_roles`，新增三张表，不引入权限角色表：

```text
admin_permission_state
  user_id          PK / FK admin_roles(user_id) ON DELETE CASCADE
  revision         bigint NOT NULL DEFAULT 0
  updated_by       FK users(id)
  updated_at       timestamptz

admin_permissions
  user_id          FK admin_permission_state(user_id) ON DELETE CASCADE
  permission       text  -- 仅全局权限
  PRIMARY KEY (user_id, permission)

admin_app_permissions
  user_id          FK admin_permission_state(user_id) ON DELETE CASCADE
  app_id           FK apps(id) ON DELETE CASCADE
  permission       text  -- 仅应用内权限
  PRIMARY KEY (user_id, app_id, permission)
  INDEX (app_id, user_id)
```

两张明细表区分全局和应用范围，避免空 app_id 和通配符语义。以应用主键绑定，不以可编辑名称/code 绑定；删除后重建同名应用不会继承旧授权。逻辑删除或被标为系统应用时，请求鉴权仍需检查应用当前状态，旧明细不产生访问能力；清理明细需走同一策略锁与修订号更新流程。

应用禁用仅控制业务访问，不移除管理员维护该应用的授权，以便有权限的管理员重新启用。若后续增加删除或系统标记变更入口，须在策略锁内移除对应授权、递增受影响管理员 revision、记录差异并撤销其会话，不能仅依赖外键级联而绕过授权版本更新。

`admin_permission_state` 用于全局与全部应用授权的统一版本和并发控制；空权限也有版本，不依赖明细行是否存在。权限代码在后端 Rust 枚举/静态目录维护，含名称、scope 类型、分组、依赖与风险提示，前端通过超级管理员接口读取，避免维护两套目录。数据库中的未知代码或错误 scope 类型不产生任何授权。

新增普通管理员初始化为空权限。移除管理员、升级为超级管理员时删除权限状态及明细；超级管理员降级为普通管理员也从空权限开始，不能恢复历史权限。身份与明细不一致时拒绝普通管理员访问并记录异常。

## 7. 保存、撤权和并发语义

采用“替换完整集合”，请求包含目标 ID、期望 revision、global_permissions、app_grants、CSRF token。app_grants 的每一项包含具体 app_id 与该应用 permissions，重复应用 ID/重复权限拒绝或在规范化后比较。接口可为 `POST /dashboard/admins/{id}/permissions`；目录接口 `GET /dashboard/admins/permission-catalog`；现有管理员列表附带完整授权与 revision。三个入口均仅超级管理员可访问。

```json
{
  "revision": 3,
  "global_permissions": [],
  "app_grants": [
    {"app_id": "应用A的UUID", "permissions": ["apps.read", "clients.read", "clients.manage"]},
    {"app_id": "应用B的UUID", "permissions": ["apps.read"]}
  ],
  "csrf_token": "..."
}
```

全局和应用集合必须显式提交，不能缺字段时静默当作保留或清空。移除 app_grants 中的某个应用表示撤回该应用全部权限，不影响同一管理员其他应用的授权。

事务顺序：获取现有 `admin::lock_policy` → 锁定操作者/目标并重新校验身份与会话 → 比较 revision → 校验权限目录、作用域、应用有效性及各范围内依赖 → 替换两类集合、递增 revision → 写入授权差异审计 → 撤销目标所有登录状态 → 提交。revision 冲突返回 409，要求刷新后重新比较，不能覆盖另一位超级管理员刚做的变更。规范化后相同集合可作为无变更返回，不撤销会话。

首期每次后台请求从主库读取最新身份和权限，不将授权结果保存在长期 JWT、Cookie、浏览器缓存或 Redis 中。权限变化后沿用现有角色变化的会话撤销策略，目标需重新登录完成 MFA。

所有普通管理员后台写事务也先取同一策略锁，再重新校验操作者和目标身份，直至业务提交。用户创建、修改、密码重置、客户端、通知重试等相关服务需要统一适配锁顺序。这样撤权/身份提升与业务写入有确定顺序：先提交的业务操作可能完成；撤权提交后，旧权限不能再提交新的业务写入。仅在中间件读一次权限不能提供此保证。

该锁会串行化管理写操作，适合本期低频控制台；不扩大到所有登录或普通用户业务。后续只有出现可测量的竞争再细化锁粒度。读取请求在已授权后可能与撤权并发完成，不能声称追回已发送数据。

## 8. 路由落地约定

| 路由/动作 | 所需权限 |
| --- | --- |
| GET 用户列表、详情 | `users.read`，附加敏感区块另检 |
| GET/POST 用户新建 | `users.create` |
| GET 用户编辑 | 至少一个可编辑能力，按字段返回；联系方式另检敏感读取 |
| POST 用户 edit | 按实际修改字段检查 `users.update` / `users.contact.update`；建议拆动作 |
| POST 用户 set-status / reset-password | `users.status.update` / `users.password.reset` |
| POST 用户 grant-app / revoke-app | 目标应用的 `apps.members.manage`，检查用户和应用两端；不要求全局 users.read，也不返回全局用户详情 |
| GET 应用列表 | 按各应用 `apps.read` 过滤后分页、计数 |
| GET 应用详情 | 该应用 `apps.read`，客户端/成员区块另检 |
| GET 应用 new、POST 应用创建 | 仅超级管理员 |
| GET 应用 edit、POST 应用 edit/toggle | 该应用 `apps.manage` |
| POST 客户端 new/edit/toggle | 真实归属应用的 `clients.manage`，编辑密钥变化另检 |
| POST 客户端 reset-secret | 真实归属应用的 `clients.secret.rotate` |
| GET 应用成员列表（新增） | 该应用 `apps.members.read` |
| POST 应用成员候选精确解析（新增） | 该应用 `apps.members.manage`，最小摘要、CSRF、速率限制 |
| GET 提供方列表、详情 | `providers.read`，仅摘要；编辑表单仅超管 |
| GET events / audit / notifications | 对应 `.read` 权限 |
| POST notifications/{id}/retry | `notifications.retry` |
| 管理员、授权接口、提供方写操作、密钥写操作 | 仅超级管理员 |

`/dashboard` 跳转到第一个有权访问的模块，不能固定去 apps。无权限管理员显示“尚未分配权限”，可回个人中心；仍不能进入模块接口。HEAD 沿用对应 GET 的授权和字段规则，不将未知方法当成读取。

前端 layout 增加身份、当前全局权限及 has_visible_apps 导航标志；应用页面返回该应用的有效权限，列表按行附带所需操作能力。普通管理员响应不能携带其范围外的应用目录。菜单、编辑按钮、详情区块均按相应范围的权限显示，应用页面的“用户”入口显示为“本应用成员”，不能误导为全局账户管理。后端永远独立检查，不信任客户端传回的权限数组。

## 9. 授权界面与审计

在现有管理员页增加普通管理员的“分配权限”，分成“全局权限”和“应用权限”。全局用户账户权限明确提示影响所有非管理员账户；应用权限先选择应用，再逐个应用勾选业务能力，可复制一组勾选到多个明确选中的应用。显示已选应用/权限数量、高影响能力说明以及保存前按应用展开的新增/移除差异。

空应用授权表示无访问权，移除应用时明确展示将撤回的权限。“全选当前应用”不包含系统应用或未来应用；无默认自动勾选。普通管理员不显示授权入口；仅在前端隐藏并不足够，接口必须拒绝。

授权变更事务写结构化审计：操作者 ID、目标管理员 ID、before/after revision、added/removed 的 scope 类型、app_id（应用授权时）和权限代码、时间及请求编号。不得存完整表单、凭据或联系方式。审计写失败回滚授权和会话撤销，不能出现授权成功却没有变更记录。

沿用后台写 pending 审计；需要让已认证管理员的授权拒绝也进入结果记录，避免在现有 audit 包装前直接返回而丢失记录。权限分配的成功差异作为事务内权威记录，禁止仅依赖响应后的 outcome 更新。

## 10. 迁移和验收

权限表包含在合并后的初始迁移，普通管理员默认无权限，超级管理员保持原能力。

必要验收覆盖：

1. 未分配、已分配、撤回权限；直接请求隐藏接口、HEAD、伪造权限和未知路由均默认拒绝。
2. 普通管理员授予自己/别人权限、修改超管/同级/自己的后台账户、变更系统应用及其客户端全部失败。
3. 替换 URL UUID、表单 app_id、搜索条件或跨资源引用无法访问受保护对象；空列表的计数也不泄漏管理员数量。
4. `users.update` 无法改联系方式；无敏感读取时响应不含完整邮箱/手机；无客户端读取时应用详情不含客户端配置。
5. 无密钥轮换权限时，reset-secret 和 edit 注入 secret/变更类型均被拒绝；客户端新建的一次性 secret 不写入审计。
6. 两位超管同时保存发生版本冲突；撤权与写入、用户提升为管理员与重置密码并发时符合事务顺序。
7. 身份移除/升级/降级后不残留可恢复权限；禁用用户、MFA、近期认证、最后有效超管保护保持生效。
8. 数据库/审计故障拒绝授权且无部分提交；授权后目标旧会话失效；无依赖权限的集合无法保存。
9. 每条 `/dashboard` 路由都声明权限或超管专属策略，新增路由缺声明时验证失败。
10. 管理员可管理 A、只读 B、不可见 C：A 的权限不能用于 B/C；替换客户端 ID、路径/表单 app_id、修改客户端归属均不能越界。
11. 应用列表、成员、客户端、全局用户详情内的应用关系、计数与选择器均按范围过滤；应用管理员无法读取成员其他应用关系或全局联系方式。
12. 应用成员管理不授予共享账户密码、状态和联系方式修改能力；全局用户管理也不自动获得任何应用访问分配能力。
13. 全局权限放入应用集合、应用权限放入全局集合、依赖仅存在于另一应用、伪造系统/已删除应用授权均整笔失败。
14. 新应用不继承旧授权；撤回 A 不改变 B 的权限明细；同名应用重建不继承旧 app_id 的授权；应用删除/系统标记变化与授权保存并发时无失效授权生效。
15. 无全局 events/audit/notifications 权限时，应用范围不能被用于推断全局日志/通知访问；成员候选查询不会返回全局目录、管理员或联系方式。

## 11. 参考与取舍

- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：采用最小权限、默认拒绝、逐请求验证以及授权测试原则。
- [Kubernetes RBAC：防提权与授权绑定限制](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#privilege-escalation-prevention-and-bootstrapping)：借鉴“使用业务权限”和“分配权限”必须受独立限制的思想。本项目直接限定超管分配，不引入 bind/escalate 等额外授权能力。

上述表结构、19 项权限和保护规则为本项目方案，不是照搬外部系统。通过全局授权加显式应用授权满足动态分配和应用隔离；只有出现大量重复分配时再考虑权限组，不为本期增加角色继承或策略语言。
