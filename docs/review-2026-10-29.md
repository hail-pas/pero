# 项目审查（2026-10-29）

基于当前工作区进行审查，保留已有未提交功能改动。重点检查 OAuth 客户端认证、授权码与刷新令牌、会话撤销、管理员权限、MFA/恢复流程、外部 HTTP 请求、迁移和部署，并运行现有回归。

## 已处理问题

- **启动与数据库版本脱节**：原先启动只建立连接，遗漏手动迁移会让不匹配的 schema 接收业务流量。现在服务和 bootstrap 在启动业务前自动迁移并验收。
- **历史核对不足**：原脚本只检查本地文件对应的 checksum，没有拒绝数据库中的未知版本。现在历史必须是当前发布迁移的完整前缀，未知版本、缺失前序记录和校验和不匹配均拒绝启动。
- **缺少迁移后验收**：原流程执行完 SQL 即提交。现在在同一事务内检查必要表字段、关键唯一索引、恢复凭据配对约束、注销/通知触发器和种子数据，失败回滚；无待迁移版本时也会验收。
- **HTTP 任务退出后进程仍存活**：主进程原先只等待系统信号，HTTP 任务意外结束时可能保留无服务能力的进程。现在同时监控该任务，清理资源并以失败状态退出。

合并原 11 个迁移为一个初始版本，删除空库不需要的数据回填、升级时会话撤销和旧字段创建后再删除的步骤。迁移实现统一在 Rust 内，部署不再执行散装 SQL，也不再依赖 psql 和 Perl SHA 工具；初始化数据库连接 URI 不再作为 psql 的命令行参数。后续迁移在构建时自动收集，不增加新的运行依赖。

## 本轮独立复核补充

在上述已有工作区改动上复核认证/令牌、管理员授权、MFA/恢复、第三方登录、外部 HTTP、迁移及前端请求处理。本轮没有确认新的高危漏洞；这不代表覆盖了所有路径或证明不存在漏洞。

- **P2：Bearer 认证响应头格式错误（已修复）**：`www_authenticate_value()` 原先把认证方案和参数一起用逗号拼接，输出 `Bearer, error="invalid_token"`。按标准解析的 OAuth 客户端可能无法把错误参数关联到 Bearer challenge，从而影响认证失败及刷新处理。现在输出 `Bearer error="invalid_token"`，后续参数才使用逗号分隔。依据：[RFC 6750 §3](https://www.rfc-editor.org/rfc/rfc6750#section-3)。新增一条回归，覆盖有/无 realm 的响应格式。
- **删除未使用的 API**：移除仓库无调用的 `default_title`、`as_oauth2_error`、`with_status`、`with_realm`；其中 OIDC 转 OAuth 方法还会丢失原 OIDC 错误码，保留并无益处。
- **统一上游 HTTP 失败处理**：请求扩展的 `send()` 已统一拒绝非 2xx，删除 OAuth/微信/邮箱查询中的五处重复 `error_for_status()`，以及 back-channel 投递中不可达的非成功状态分支。失败仍由共享 HTTP 层拒绝，不改变重试规则。

- **集成测试并发导致随机失败（已修正运行命令）**：默认并行运行现有安全集成测试时，多个用例争抢进程内仅 4 个密码计算名额，复现 2 个 `crypto_busy` 失败。这是测试相互干扰，不能通过放宽生产资源限制解决。CI 和 README 的专用集成测试命令统一加入 `--test-threads=1`；单个用例内已有的并发安全场景仍正常执行。

依赖核查：pnpm audit 报告 0 项漏洞；OSV 检查 436 个 Rust 包，无未处置发现，仍有已有策略精确列出的 1 项、截至 2026-11-28 的误报豁免。本轮未调整依赖版本，也未增加抽象层。

## 第二轮复核补充

继续检查会话撤销、权限变更、账号恢复、联系方式写入、连接配置及部署脚本。保留前述修复和已有未提交功能改动，仅处理以下两个可复现的问题：

- **连接 URL 查询参数泄露凭据（已修复）**：`TypedUrl` 原先只遮盖 authority 中的密码。SQLx 0.9 的 PostgreSQL 解析器也接受 `?password=...`，数据库初始化又会通过 `Display` 记录连接地址，因此该形式的密码会进入 INFO 日志；连接 `options` 也可能携带应用加密密钥。现在诊断表示省略查询参数和片段，继续遮盖 authority 密码。`Display`、`Debug` 和序列化共用该表示；`expose_secret()` 仍返回完整原始连接配置，实际连接参数不变。新增一条 URL 回归，修复前复现泄露、修复后通过。
- **管理员联系方式修改绕过格式校验（已修复）**：自助修改会检查邮箱/手机号，管理员服务却直接写入。通过管理接口提交 `email=invalid-address`，修复前返回 HTTP 200 并覆盖原邮箱，导致后续验证通知/恢复无法使用该地址。现在服务层在权限检查后复用 `ContactChannel::is_valid_format()`，非法值返回 HTTP 400 并保留原值；删除联系方式仍使用原有的空值语义。在已有权限集成用例中补充邮箱和手机号断言，修复前复现失败、修复后通过。
